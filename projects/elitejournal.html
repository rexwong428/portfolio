Tools

Constraint

The problem the data creates

A trading journal is only as good as the executions behind it. The broker API does not keep those executions available indefinitely: recent fills can be pulled, older ones drop off and cannot be requested again at any price. That single fact changes the whole shape of the work. Ingestion is not a convenience feature that can be retried tomorrow, it is a deadline. If a sync silently stops on a Friday, by Monday the data is gone permanently.

Capturing before the window closes

Each account carries a watermark recording how far its data has actually been read, so a sync resumes from the last confirmed position rather than from an assumption. Accounts whose connection has lapsed are surfaced as a list to act on, instead of quietly returning zero rows and looking healthy. Where an account is connected late, historical backfills pull whatever the broker still holds, and the boundary between backfilled and live data is recorded rather than blurred.

Reconciling, not just importing

Fills arrive from the API, but statements and CSV exports also arrive by hand, in a different shape from every broker. Both paths land in one trade model so that analytics cannot disagree with the journal, and the imported set is reconciled against the account's own cash and balance records rather than trusted on arrival. The parsers handle the real formats people actually export, including accounting style negatives written as bracketed amounts, which a naive numeric cast reads as text or as a positive number.

Fees are point in time

Commission and fee rates change. If the rate is looked up at report time, editing today's rate silently rewrites last year's P&L, and every historical number moves without anyone touching a trade. So rates are snapshotted onto each trade at the moment it is synced, and reporting reads the snapshot. Re-pricing older trades is possible, but it is a deliberate action with a visible result rather than an accident.

Making the import configuration data, not code

Brokers and fee schedules are held in a table, not hardcoded across components. The import options, the connection flow and the admin fee screens all read from that one source, so adding a broker or a new export format is a data change plus a parser, rather than an edit in several places that will fall out of step. It also means the fee schedule can be inspected and corrected by someone who is not reading the code.

What I would call the lesson

Most reporting problems in this system were never reporting problems. They were a sync that stopped without saying so, a rate that was read at the wrong time, or two tables that were each partly right. Fixing the number in the dashboard would have hidden all three. The work worth doing was upstream, where the record is either captured correctly or lost.
